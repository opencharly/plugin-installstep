# 2026.326.0802 — fix(builder)!: a pod-overlay builder step never opens a stage, and a missing context fails

## Summary

A pod-overlay builder step never opens its own stage, and a missing context is loud (opencharly/sdk#608).

- A multi-stage builder (`pixi`/`npm`/`mise`/`aur`) emits NO stage from the step. The image — box build or pod overlay — hoists the stage before its main `FROM` and copies the payload (`EmitBuilderStages`/`EmitBuilderArtifacts`, one path for both modes, D-IR-1). A stage rendered here landed mid-file, after the main `FROM`, so the builder stage became the image and nothing was copied back.
- The step's only output is a declared PACKAGE output the distro serves through `local_pkg`, rendered by the one shared `deploykit.RenderBuilderPackageInstall`.
- A missing image, builder vocabulary or candy is now a hard error naming candy and builder. It used to emit a `# Builder: … skipped` comment, which baked an image without the build.

**Dependencies.** `go.mod` moves the `github.com/opencharly/sdk` and `github.com/opencharly/spec` pins to `v0.2026326.342` (sdk#613) and `v0.2026326.323` (spec#420), both merged and tagged. The `go` directive and the indirect block move with them (the new sdk's own directive and import closure, added by `go mod tidy`), and `go.sum` records exactly those modules.

**This repo is a contract / library module** in the R10 sense: its root `charly.yml` is a `discover:` manifest with no `box:`/`deploy:`/`check:` node, so no bed can exist here (proof below). Its class gate is its own module suite. The live end-to-end proof is owed by the chain on opencharly/sdk#608; this PR posts `WAITING` on it and the matching `HOLDING` there.
