# 2026.276.0440 — fix(deps)!: adopt the typed ExtraCandyRef (spec#188 consumer)

## Summary

Adopts `spec v0.2026273.203` + `sdk v0.2026276.48`, which is the type change `spec#188` made: an `ExtraCandyRef` now carries its **SCOPE**, so `spec.ResolvedProjectRequest.ExtraCandyRefs` is `[]spec.ExtraCandyRef{Ref, Scope}` instead of `[]string`.

**Why this repo is in the wave.** Every compiled-in plugin candy is a `require` pin in charly's `go.mod`, resolved from the module proxy, so when `sdk`'s own main moved its `spec` require to `v0.2026273.203` (`sdk#325`, merged), any charly that adopts that sdk stops compiling this candy. `plugin-build`, `plugin-fleet` and `plugin-installstep` are the three; this is the `plugin-installstep` leg.

**This leg's pin had drifted the furthest.** This module was still on `sdk v0.2026241.2117` / `spec v0.2026241.1322` — about a month behind the other two, which were already on the `...272` pair. So this is the largest `go.mod` in the wave, and two of its changes are **forced, not chosen**:

1. **`plugin.go` (+1/−1)** — the only code change. `getGenerator` forwards the host's refs *verbatim* into the resolved-project request, so only its parameter type changes. This plugin makes no scope decision of its own: it is not the owner of the refs it forwards, and the scope travels through untouched. (`env.ExtraCandyRefs` at the call site is already typed, which is why this one signature retype fixes both compiler sites.)
2. **`candy/plugin-installstep/go.mod` (+11/−6)** — the sdk/spec bump, plus two indirects the newer sdk pulls in (`opencontainers/go-digest`, `opencontainers/image-spec`) and the `golang.org/x/{net,sys,term,text}` chain, which MVS raises because the newer sdk/spec require it. None of these is a choice made here.
